## 1. Ringkasan Eksekutif (Abstract)

RFC ini mengusulkan kerangka kerja modular generasi berikutnya untuk Aurion Protocol menggunakan pola **Capability-Based Keeper**. Pola ini mengadaptasi keunggulan modularitas dinamis *web application framework* (seperti apps di Django atau packages di Laravel) dan arsitektur *sovereign state machine* (seperti Cosmos SDK `x/` modules dan Substrate FRAME), namun disesuaikan secara ketat dengan batasan protokol Aurion: **Zero-Unsafe, Zero-Float (`u64` Quanta), Zero-Unwrap, dan isolasi CQRS/SMR tanpa tumpukan RPC konvensional**.

Kerangka kerja ini memberikan jaminan:
1. **Isolasi State Mutlak:** Tidak ada modul yang dapat mengakses atau merusak *storage* modul lain tanpa izin eksplisit (*Capability Grant*).
2. **Komposabilitas Tanpa Tumpukan (Decoupled Wiring):** Modul-modul baru dapat dihubungkan ke simpul (*plug-and-play*) saat *runtime assembly* tanpa mengubah mesin konsensus BFT atau mesin penyimpanan dasar `redb`.
3. **Eksekusi Atomik & Deterministik:** Mutasi state multi-modul dalam satu transaksi dieksekusi secara *all-or-nothing* melalui *Transactional Cache/Sub-store*.

## 2. Latar Belakang & Masalah (Motivation)

Arsitektur monolitik blockchain konvensional umumnya menghadapi dua jebakan arsitektur:
1. **Model Monolitik Kaku (Rigid Spaghetti State):** Seluruh logika transaksi (transfer, tata kelola, validator) membaca dan menulis ke satu tabel state global tanpa batas domain yang jelas. Penambahan fitur baru berisiko merusak logika yang sudah ada (*side-effects*) dan memperumit migrasi data.
2. **Ketergantungan Eksternal via RPC/HTTP:** Komunikasi antar-layanan sering kali dilempar ke lapisan middleware JSON-RPC yang lambat, boros alokasi heap memori, dan non-deterministik.

Aurion membutuhkan sistem modular yang sedinamis arsitektur MVC web modern, namun mempertahankan disiplin mutlak *State Machine Replication* (SMR):
$$S_{n+1} = f(S_n, \text{Block})$$

## 3. Desain Arsitektur: Pola Capability-Keeper

Pola ini memisahkan logika bisnis modul dari hak akses penyimpanan fisik menggunakan tiga pilar utama: **StoreKey**, **Keeper**, dan **Capability Grants**.

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        AURION RUNTIME ASSEMBLY                         │
│                                                                        │
│   [Master KV Store / redb] ──► [StoreKey: Bank] ──► BankKeeper         │
│                            ──► [StoreKey: Stak] ──► StakingKeeper      │
│                            ──► [StoreKey: Gov ] ──► GovKeeper          │
│                                                          │             │
│                                                          ▼             │
│   StakingKeeper diizinkan membaca/memotong saldo via:   │             │
│   BankKeeper (Hanya melalui trait ReadBalance + Mint/Burn Capability)  │
└────────────────────────────────────────────────────────────────────────┘

```

### 3.1. StoreKey & SubStore (Isolasi Partisi Data)

Setiap modul hanya menerima pointer partisi terisolasi (*StoreKey*). Modul tidak memiliki referensi langsung ke instance `redb` pusat.

* Setiap `StoreKey` memiliki namespace unik berupa prefix biner 4-byte (misal: `b"bank"`, `b"stak"`, `b"gov_"`).
* Operasi baca/tulis melalui `StoreKey` otomatis di-prepend dengan prefix namespace tersebut, mencegah terjadinya tabrakan kunci (*key collision*).

### 3.2. Struktur Keeper (Pengelola Domain)

Setiap modul mendefinisikan sebuah struct `Keeper`. `Keeper` bertindak sebagai *Controller* internal modul yang memegang otoritas atas `StoreKey` miliknya:

```rust
// Contoh: Keeper Modul Saldo (Bank)
pub struct BankKeeper {
    store_key: StoreKey,
}

// Contoh: Keeper Modul Staking yang butuh akses potong/tambah saldo
pub struct StakingKeeper<B: BankCapability> {
    store_key: StoreKey,
    bank_keeper: B, // Dependency Injection via Trait
}

```

### 3.3. Capability Trait (Prinsip Hak Akses Terkecil)

Jika Modul Staking memerlukan interaksi dengan Modul Bank, Modul Staking **dilarang** memanggil fungsi mutasi bebas milik Bank. Akses dibatasi menggunakan *Capability Trait*:

```rust
/// Hak akses baca saldo (Read-Only Capability)
pub trait BankReadCapability {
    fn get_balance(&self, store: &dyn StateReader, account: &[u8; 32]) -> Result<u64, KeeperError>;
}

/// Hak akses potong/tambah saldo (Write Capability)
pub trait BankTransferCapability: BankReadCapability {
    fn transfer(
        &self,
        store: &mut dyn StateWriter,
        sender: &[u8; 32],
        recipient: &[u8; 32],
        amount: u64,
    ) -> Result<(), KeeperError>;
}

```

Dengan pola ini, jika modul pihak ketiga (misalnya `aurion-contract`) hanya butuh membaca saldo, simpul cukup menginjeksi `BankReadCapability` tanpa mengekspos fungsi transfer dana.

## 4. Siklus Eksekusi: CQRS & Transaksi Atomik

Untuk mendukung CQRS murni, antarmuka modul dibagi secara tegas antara jalur mutasi (*Command*) dan jalur pembacaan (*Query*).

```text
══════════════════════════════════════════════════════════════════════════════
                       ALUR COMMAND (JALUR TULIS / SMR)
══════════════════════════════════════════════════════════════════════════════
Tx Masuk ──► Decode Envelope ──► [Transactional Cache State]
                                           │
                                           ▼
                                 Keeper::execute()
                                    │           │
                               (Sukses)      (Gagal / Error)
                                    │           │
                                    ▼           ▼
                           Commit ke Ledger   Rollback Cache (State Asli Utuh)

══════════════════════════════════════════════════════════════════════════════
                       ALUR QUERY (JALUR BACA / VIEW)
══════════════════════════════════════════════════════════════════════════════
Kueri Path ──► Router Query ──► Keeper::query(Snapshot Imutabel) ──► Return Biner
               (Lock-Free, Bypass Konsensus, Zero Overhead)

```

### 4.1. Transactional Cache (Atomic Revert)

Sebelum modul menjalankan eksekusi transisi state, runtime membungkus state ke dalam `CacheStateWriter`.

* Seluruh operasi `set` dan `delete` hanya disimpan dalam buffer memori lokal.
* Jika seluruh tahapan transaksi sukses, buffer di-flush secara atomik ke database `redb`.
* Jika transaksi gagal di tengah jalan (misal: saldo kurang atau eksekusi logika panik terkelola), buffer dibuang seketika tanpa mencemari state ledger utama.

## 5. Kontrak Antarmuka Komposabel (`AurionAppModule`)

Setiap modul yang didaftarkan ke runtime Aurion wajib mengimplementasikan trait `AurionAppModule`:

```rust
#![forbid(unsafe_code)]

use std::error::Error;

pub struct ExecutionContext<'a> {
    pub chain_id: u64,
    pub block_height: u64,
    pub block_time: u64,
    pub sender: &'a [u8; 32],
}

pub trait AurionAppModule: Send + Sync {
    /// Namespace identitas modul (misal: b"bank")
    fn name(&self) -> &'static str;

    /// Inisialisasi data genesis saat Blok 0 dibuat
    fn init_genesis(&self, store: &mut dyn StateWriter) -> Result<(), Box<dyn Error>>;

    /// Eksekusi mutasi state (Jalur Command)
    fn execute(
        &self,
        ctx: &ExecutionContext,
        action: u16,
        payload: &[u8],
        store: &mut dyn StateWriter,
    ) -> Result<ExecutionResult, Box<dyn Error>>;

    /// Kueri state projection tanpa lock konsensus (Jalur Query)
    fn query(
        &self,
        path: &str,
        store: &dyn StateReader,
    ) -> Result<Vec<u8>, Box<dyn Error>>;
}

```

## 6. Struktur Transaksi Kanonikal (Generalized Envelope)

Format transaksi jaringan distandarisasi menggunakan pola *Envelope*:

```rust
#[derive(Debug, Clone, PartialEq, Eq, serde::Serialize, serde::Deserialize)]
pub struct TransactionEnvelope {
    pub version: u16,
    pub chain_id: u64,
    pub nonce: u64,
    pub sender: [u8; 32],
    pub fee: u64, // Quanta
    pub target_module: [u8; 4], // Prefix namespace modul (misal: *b"bank")
    pub action: u16,            // Sub-aksi di dalam modul
    pub payload: Vec<u8>,       // Parameter biner spesifik modul
    pub signature: [u8; 64],    // Ed25519 Signature
}

```

## 7. Rencana Migrasi & Fase Implementasi

Implementasi RFC-001 dilakukan secara bertahap untuk menjaga kepatuhan `Agents.md` dan memastikan kompilasi tetap bersih di setiap fase:

### Fase 1: Abstraksi Penyimpanan & Cache State (`crates/aurion-core`)

* Implementasi `StoreKey`, `NamespaceStore`, dan `CacheStateWriter`.
* Pengujian isolasi unit test pada buffer revert atomik.

### Fase 2: Standarisasi Modul Saldo Inti (`aurion-core` & `aurion-account`)

* Membungkus logika akun dan transfer saldo ke dalam `BankKeeper`.
* Mengimplementasikan `BankReadCapability` dan `BankTransferCapability`.

### Fase 3: Generalized Transaction Envelope & Router

* Memperbarui serialisasi transaksi di `aurion-core` dan `aurion-network`.
* Memperbarui validasi signature pada mempool terhadap envelope baru.

### Fase 4: Adapter Partisi Disk (`crates/aurion-ledger`)

* Memperbarui schema `redb` agar mendukung tabel terisolasi per namespace modul (`b_tree_map` partisi per prefix).

## 8. Verifikasi & Kepatuhan Invarian

Seluruh implementasi RFC-001 wajib tunduk pada gerbang keamanan yang sudah aktif:

1. **Zero-Unsafe:** Tidak ada `unsafe` dalam pembuatan pointer partisi storage.
2. **Zero-Float:** Seluruh biaya komputasi, fee, balance, dan kalkulasi rasio menggunakan fixed-integer `u64`.
3. **Audit Gate:** Wajib lolos verifikasi `tools/aurion_guard.py check` dan `cargo clippy --workspace --all-targets --all-features -- -D warnings`.
